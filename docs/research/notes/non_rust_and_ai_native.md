# Non-Rust video engines wrappable from Rust, and AI-native / MCP-enabled video editors (as of Oct 2026)

Method note: GitHub API access was blocked in this session (gh and unauthenticated curl both returned "access not enabled"), and mltframework.org did not resolve, so star counts and commit dates are mostly missing. Findings come from WebSearch/WebFetch of repo pages, distro package trackers, news sites, and MCP registries. Items marked "[background, unverified]" come from the researcher's prior knowledge, not from a source fetched in this session; the report writer should treat them as such.

## Q1. Which non-Rust engines could be wrapped from Rust, and how do they compare? (license, bindings, headless API, codecs/HW decode, GPU, color, interchange, maturity, 2026 activity)

### Takeaway
Only two non-Rust engines are serious candidates for Resolution: **MLT** (LGPL-2.1 core, very active, monthly-ish 7.x releases, powers Kdenlive and Shotcut, has a headless XML/`melt` path) and **GStreamer Editing Services** (LGPL, active 1.28.x series, has official autogenerated Rust bindings in gstreamer-rs). Neither has a typed command API, MCP server, wgpu compositor, or Resolve-grade color pipeline built in, so neither beats FilmCraft on fit; MLT is the strongest fallback on maturity, GES on Rust integration. Everything else is GPL-only, stale, alpha, a single-purpose tool, or a browser/TS engine with restrictive licensing.

### Cited Findings

**MLT Framework (Kdenlive, Shotcut)** — C/C++
- License split: the framework library is LGPLv2.1; the `melt`/`melted` applications are GPLv2; "modules should strive to be LGPL", but plugins can carry other licenses — [MLT Copyright Policy](https://mltframework.org/docs/copyrightpolicy/)
- Wikipedia lists the overall license as LGPL 2.1, GPL 2 or GPL 3 — [Wikipedia: Media Lovin' Toolkit](https://en.wikipedia.org/wiki/Media_Lovin%27_Toolkit)
- GPL plugins are packaged separately as `libmltplusgpl.so` ("This package contains GPLv2 licensed plugins") — [OpenBSD port mlt7,-gpl2](https://openports.pl/path/multimedia/mlt7,-gpl2); historically GPL modules had to be turned on with `--enable-gpl` — [RPM Fusion review thread, 2009 (Dan Dennedy)](https://lists.rpmfusion.org/pipermail/rpmfusion-developers/2009-May/005100.html)
- Latest stable release: 7.36.1, 31 Dec 2025 — [Wikipedia](https://en.wikipedia.org/wiki/Media_Lovin%27_Toolkit). The project feed (last built 6 Apr 2026) had 7.36.0 as its newest entry. That release adds linear-light image processing on the CPU (previously only through Movit) and extends 10-bit CPU processing to many more services — [mltframework.org feed](https://mltframework.org/feed.xml) (as summarized by search; the feed host did not resolve when fetched directly)
- No MLT 8 has been announced — [search summary of Wikipedia/feed](https://en.wikipedia.org/wiki/Media_Lovin%27_Toolkit)
- [background, unverified] MLT's headless interface is MLT XML plus the `melt` CLI, with C/C++ APIs (`libmlt`, `libmlt++`) and SWIG bindings. GPU compositing goes through Movit (OpenGL, GPL). It decodes through FFmpeg (libavformat), with partial hardware decode. It has OpenFX plugin support but no OCIO/ACES pipeline comparable to Resolve. I found no maintained Rust crate.

**GStreamer Editing Services (GES; Pitivi)** — C/GObject
- The official `gstreamer-editing-services` Rust crate lives in gstreamer-rs and is mostly autogenerated with gir. The docs warn that "the GES API is not Thread Safe" and recommend GES >= 1.16 — [gstreamer-rs GES docs](https://gstreamer.pages.freedesktop.org/gstreamer-rs/stable/latest/docs/gstreamer_editing_services/)
- A `-sys` crate supplies FFI bindings to libges-1.0 — [Fedora rust-gstreamer-editing-services-sys](https://packages.stg.fedoraproject.org/pkgs/rust-gstreamer-editing-services-sys/rust-gstreamer-editing-services-sys+v1_2-devel/index.html)
- GES ships in the 1.28 series: Debian has 1.28.6-1 — [Debian gir1.2-ges-1.0](https://packages.debian.org/testing/gir1.2-ges-1.0); Arch has 1.28.5 — [Arch](https://archlinux.org/packages/extra/x86_64/gst-editing-services/files/); Fedora 44 shipped 1.28.1 in March 2026 — [LinuxSecurity/Fedora advisory](https://linuxsecurity.com/advisories/fedora/gst-editing-services-fedora-44-2026-9cfb46ac78)
- 1.28 changes (secondary source, a Yocto patch summary from July 2026): a shared task pool sized to the CPU count, a new thread-safe controller API that fixes use-after-free bugs, the OTIO formatter moved to a standalone Python plugin in gst-python, controllable z-order, a GES error domain, and better timeline error reporting — [Yocto patchwork](https://patchwork.yoctoproject.org/project/oe/patch/20260729024420.2328180-15-khem.raj@oss.qualcomm.com/)
- [background, unverified] GStreamer core and GES are LGPL-2.1+, and individual plugins vary (the "ugly" and "bad" sets include GPL or patent-encumbered pieces). GStreamer has the broadest hardware-decode coverage of any option here (VA-API, NVDEC/NVENC, D3D11/12, VideoToolbox, V4L2) and has GL, Vulkan and CUDA elements. Pitivi development has been slow for years. GES has no OCIO color management.

**Olive (olive-editor)** — C++/Qt
- GPL-3.0, about 9.1k stars. The README still says "Olive is alpha software and is considered highly unstable". Binaries are offered as "0.1.0 alpha" and a "0.2.0 unstable development build" — [GitHub olive-editor/olive](https://github.com/olive-editor/olive)

- No 2026 release or roadmap was found — [search summary](https://www.videohelp.com/software/Olive-Video-Editor)
- [background, unverified] The 0.2 rewrite has a node-based compositor and OCIO color management, which were its most Resolve-like features. Lead development largely stalled after 2023.

- FreeBSD moved 0.4.0 to 0.5.0 (Python 3.12+ build fixes) — [FreeBSD review](https://reviews-dev.freebsd.org/R11:e76e0d413a8c25b4bcef2c591d15b03843a18290); openshot-qt moved 3.4.0 to 3.5.0 — [FreeBSD review](https://reviews-dev.freebsd.org/R11:575f8652b38c0c344092e96c83266b059e91210f)

- [background, unverified] libopenshot is LGPL-3.0, uses FFmpeg and Qt, does compositing on the CPU through Qt/QImage, has a JSON timeline API, and has no OCIO. The Qt dependency and the CPU compositor make it a poor fit for a wgpu, Resolve-class engine.

**Blender VSE (bpy headless)** — C/C++/Python, GPL-2.0-or-later

### Inferences
- **License implications for a private derivative:**
  - **MLT** (LGPL core): dynamic linking of libmlt from a private Rust binary is fine. You must avoid the `plusgpl`/Movit/`melt` GPL parts, or run them out of process. Static linking under LGPL brings relinking obligations if you ever distribute.
  - **GES/GStreamer** (LGPL): the same applies. Dynamic linking through gstreamer-rs is the standard, well-trodden path. Leave out GPL "ugly" plugins.
  - **libopenshot** (LGPL-3): dynamic linking is fine, but LGPL-3's anti-tivoization terms apply if it ships on locked devices.
  - **Olive, Blender, Natron, Cinelerra-GG, Flowblade, LosslessCut, Movit** (GPL): usable only as a separate process over IPC. Even then, a tightly coupled design (shared data structures) risks being judged a derivative work. A private repo that is never distributed has no GPL obligations, but that stops holding once the project is open-sourced or shipped.
  - **Remotion, Diffusion Studio**: commercial/source-available licenses that are incompatible with a later MIT/Apache open-source release.
- **Rust bindings exist only for GES** (official, gir-generated) and OTIO (community, Linux-only). MLT would need a hand-written `bindgen` crate over its C API. That is feasible: the C API is small and stable.
- **Fit to Resolution's design:** none of these engines offers what FilmCraft gives Resolution directly: a typed command API with 650+ commands, an MCP server, a wgpu compositor, or OCIO/ACES color. Wrapping MLT or GES would mean building the command/undo/MCP layer, a GPU compositor, and color management on top. That is most of the work FilmCraft has already done, plus a C dependency stack (FFmpeg/GStreamer) to package for three operating systems.
- **Where non-Rust engines beat FilmCraft:** maturity and codec coverage. MLT and GStreamer, through FFmpeg and hardware-decode plugins, handle real-world camera formats (ProRes, DNxHR, H.264/H.265 10-bit, BRAW is not covered by either) far more completely than a pre-alpha pure-Rust codec stack is likely to. A pragmatic hybrid is to keep FilmCraft's timeline, command and MCP layers and add a GStreamer- or FFmpeg-based decode backend behind a trait. That is probably a better contingency than swapping engines wholesale.
- **Ranking as a fallback engine:**
  1. **MLT**: most production-proven NLE engine, very active, LGPL core, XML project format, headless `melt`, used by two major editors.
  2. **GES**: official Rust bindings and the best hardware decode, but a smaller NLE community (Pitivi is slow), a non-thread-safe API, and weaker NLE semantics.
  3. libopenshot: LGPL, but CPU/Qt compositing.
  
  Olive is the most Resolve-like in architecture (nodes, OCIO), but it is GPL and stalled alpha software, so it is not viable.

## Q2. What AI-native / MCP-enabled video editors and MCP servers exist, and what tool surfaces do they expose?

### Takeaway
The MCP video ecosystem in 2026 is crowded but almost entirely **bolt-on bridges**: wrappers over an existing application's scripting API (Resolve, Premiere/After Effects, Kdenlive D-Bus) or over FFmpeg CLIs. The most mature examples are samuelgursky/davinci-resolve-mcp (MIT, about 3.4k stars, 37 compound tools / 389 granular tools) and Kinocut (Apache-2.0, 203 FFmpeg-backed tools). Few projects are AI-native editors with their own timeline (OpenChatCut is one). None is an engine-plus-MCP built together the way FilmCraft claims to be, so FilmCraft's built-in MCP is a real differentiator.

### Cited Findings

**DaVinci Resolve MCP servers** (all use Resolve's Python scripting API, and Studio is generally required)
- **samuelgursky/davinci-resolve-mcp** (MIT, about 3.4k stars, v4.10.3):
  - Ships a "compound" server with 37 tools covering 136 guarded actions, a "granular" server with 389 tools (one per API method), and an optional Node "advanced" server with 18 offline tools for `.drp/.drt/.drx` files and project databases that works without Resolve running.
  - Every compound response uses a shared `_operation` envelope.
  - Transport is local stdio. The optional networked transport binds to loopback and requires a per-launch bearer token.
  - A free-edition in-app bridge re-exports the `resolve` object over HMAC-signed loopback requests with one-use nonces. It is validated on 21.0.x, but on free 21.1 the Scripts menu no longer lists `.py` files, so the bridge is "supported-until-it-is-not".
  - Guardrails: source media is immutable; destructive actions follow plan, review, then confirm, with dry runs; `destructive.safe_mode` and an audit log; the timeline is archived before mutation; `CopyGrades` is refused unless `acknowledge_trap: true` is passed; `inspect_operation` returns a risk level and blast radius; known limitations are attached as compact `known_limitation` objects to keep responses small; execution traces omit parameters and paths.
  - Source: [GitHub samuelgursky/davinci-resolve-mcp](https://github.com/samuelgursky/davinci-resolve-mcp)
- **hoyt-harness/davinci-mcp-professional** (GPL-3.0): a "kernel + domain" design. Six kernel tools are always loaded (`activate_domain`, `deactivate_domain`, `list_domains`, `get_version`, `get_current_page`, `switch_page`). 289 domain tools across 9 domains load only on activation, through `notifications/tools/list_changed`. "Context cost at session start is bounded by the kernel alone." Requires Studio — [GitHub](https://github.com/hoyt-harness/davinci-mcp-professional)
- Other Resolve servers:
  - DigitalWorkflowCompany/resolve-mcp: Resolve 21, 88 tools plus 20 resources, macOS — [GitHub](https://github.com/DigitalWorkflowCompany/resolve-mcp)
  - lordhoell/davinci-resolve-mcp: "440+ tools" plus a Claude Code skill, Resolve 19+ — [GitHub](https://github.com/lordhoell/davinci-resolve-mcp)
  - hiteshK03: 44 tools, free edition through an in-app bridge, local Whisper — [GitHub](https://github.com/hiteshK03/davinci-resolve-mcp)
  - apvlv: includes raw `execute_python`/`execute_lua` escape hatches — [GitHub](https://github.com/apvlv/davinci-resolve-mcp)
  - Tooflex: 32 tools plus 6 read-only resources. Resolve's scripting module still imports `imp`, so it needs CPython 3.10/3.11 — [GitHub](https://github.com/tooflex/davinci-resolve-mcp)
  - wassermanproductions/unofficial-davinci-mcp (Apache-2.0): free-edition FCPXML/LUT workflows, beat-aware cuts, dialogue tightening, loudness, and a voice bridge — [GitHub](https://github.com/wassermanproductions/unofficial-davinci-mcp)

### Inferences
- **Two tool-surface philosophies dominate:**
  - Granular, one-tool-per-API-method surfaces (389 to 440+ tools) give complete coverage but overflow agent context.
  - Compound or domain-loaded surfaces (37 compound tools; a 6-tool kernel plus lazy domains) are what the most mature projects now recommend.
  
  FilmCraft's 650+ typed commands will hit the same problem if each is exposed as its own MCP tool.
- **Every Resolve MCP is limited by Blackmagic's scripting API.** It needs Studio, Python 3.10/3.11 because of `imp`, and the free-edition bridge path is closing in 21.1. This is a strong argument for an editor whose engine *is* the API, which is Resolution's thesis.
- **The AI-native editors with their own timeline are young and either AGPL (OpenChatCut) or FFmpeg-pipeline tools (Kinocut).** None is a credible engine to build on, but they are good references for agent UX: transcript-based editing, filler and silence removal, receipts and provenance.

- Star counts and activity for most MCP repos other than samuelgursky and Kinocut were not verified.
- OpenChatCut's repo URL and license were not confirmed from a primary source.
- No generic, well-known FFmpeg MCP server other than Kinocut was examined in detail.
- No Shotcut, Blender-VSE or OpenShot MCP server was found. There may be Blender MCP servers (for example a general blender-mcp), but they were not searched.
- No official MCP from Blackmagic, Adobe, Avid or Apple was found.

## Q3. Lessons for Resolution's MCP layer, and verdict: does any non-Rust engine beat FilmCraft? Best fallback?

### Takeaway
No non-Rust engine beats FilmCraft for Resolution. The decisive differentiators are a permissive license, pure Rust, a typed command API with MCP built in, and a wgpu compositor, and none of the alternatives offers that combination. **MLT (dynamically linked LGPL core, GPL modules excluded) is the best fallback engine**, with **GES via gstreamer-rs** as the runner-up, or as a decode/hardware-acceleration backend under FilmCraft. The best MCP design patterns to copy come from samuelgursky/davinci-resolve-mcp, hoyt-harness and Kinocut.

### Cited Findings
- Compound tools with an action parameter and one shared `_operation` response envelope keep context low; a granular mode is kept as an option — [samuelgursky](https://github.com/samuelgursky/davinci-resolve-mcp)
- Lazy domain loading through `activate_domain` and `notifications/tools/list_changed` bounds session-start context to six kernel tools — [hoyt-harness](https://github.com/hoyt-harness/davinci-mcp-professional)
- Safety patterns:
  - Plan, review and confirm for destructive actions, with dry runs; a snapshot of the timeline before mutation; `acknowledge_trap` flags for known-dangerous operations; `inspect_operation` returning risk and blast radius; immutable source media with sidecar analysis output; a trace log without parameters — [samuelgursky](https://github.com/samuelgursky/davinci-resolve-mcp)
  - Preflight validation before rendering; hash-chained "receipts" with resume cursors; a `search_tools` discovery tool; fail-closed human approval — [Kinocut](https://github.com/KyaniteLabs/mcp-video)
- Offline project-file tools (18 tools over `.drp/.drt/.drx` without Resolve running) show the value of separating headless operation from the GUI — [samuelgursky](https://github.com/samuelgursky/davinci-resolve-mcp)
- Loopback-only networked transport with a per-launch bearer token, and an HMAC-plus-nonce in-app bridge — [samuelgursky](https://github.com/samuelgursky/davinci-resolve-mcp)
- A missing per-session draft/version layer for external agents was the self-reported gap in OpenChatCut — [search summary of Product Hunt listing](https://www.producthunt.com/products/openchatcut)

### Inferences
- **Recommendations for Resolution's MCP layer:**
  1. Don't expose 650+ commands as 650+ tools. Use roughly 10 to 40 compound, page- or domain-scoped tools that mirror Resolve's pages (Media, Cut, Edit, Fusion, Color, Fairlight, Deliver), loaded lazily with `tools/list_changed`, plus `search_tools`/`describe_command` for the long tail.
  2. Use one uniform result envelope with operation id, diff and undo token.
  3. Give every mutating command a dry-run/preview mode and an undo-group id. Agent sessions should work on a branch or draft timeline that the user merges, which closes the gap OpenChatCut admits.
  4. Keep source media immutable, and put analysis output (transcripts, scene cuts) in sidecars.
  5. Use risk tiers with explicit acknowledgment flags for destructive or irreversible operations.
  6. Write provenance and trace receipts.
  7. Bind transport to stdio by default and loopback-plus-token for HTTP.
  8. Have the headless engine own the API, so the GUI is just another client. This avoids the Studio-only, Python-version-pinned trap every Resolve MCP faces.
- **Verdict:** FilmCraft remains the front-runner. Its risks (pre-alpha, a small team, an in-house codec stack) are real. The mitigation is to put decode/encode and possibly compositing behind traits, so that an FFmpeg- or GStreamer-based I/O backend can be added. That beats swapping in MLT or GES wholesale.
- **If FilmCraft fails entirely:**
  1. **MLT** (dynamic LGPL linking, bindgen crate, MLT XML as an internal or interchange format, GPL plugins excluded or run out of process) is the most mature NLE engine.
  2. **GES** is better if first-class Rust bindings and hardware decode matter more than NLE maturity.
  
  In both cases Resolution would still need to build its own command/undo/MCP layer, GPU compositor (wgpu) and OCIO color pipeline. Olive's node/OCIO design is a reference architecture only, since it is GPL and stalled.
- Web engines (Remotion, Diffusion Studio, Twick) are disqualified for a native Rust desktop editor by both runtime (browser/Node) and license (Remotion's company license; Diffusion Studio's commercial license after v1).

### Gaps
- No head-to-head performance or format-coverage data was found for FilmCraft's codecs versus FFmpeg-based engines.
- Whether anyone has shipped a Rust application on MLT (via FFI) in production was not found.
- Native BRAW/R3D support in any open engine was not researched; only proprietary SDKs are likely to provide it [background, unverified].
